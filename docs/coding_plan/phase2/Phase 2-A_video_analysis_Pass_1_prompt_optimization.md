## 二、当前提示词的问题分析

### 问题 1：缺少合并/间隔策略 → 碎片化片段

从日志可以看到，同一个视频产出了两个片段 `00:00-00:05` 和 `00:18-00:44`，中间的 00:05-00:18 被过滤掉了。但如果这 13 秒中只是一次短暂的捡球/换球（比如 3-5 秒），那前后两段练习其实应该合并为一个片段。

**当前提示词**没有给出任何合并策略指引，导致：
- 模型容易对每一次短暂停顿都切断片段
- 产出大量碎片化的短片段（增加后续分析 token 消耗）
- `validateSegments` 的 20 段上限更容易被触发

### 问题 2：缺少对"边界"的精确定义

"有效击球"的开始和结束时刻如何界定？当前提示词只说了"包含实际击球动作的片段"，但没有明确：
- 开始：从引拍/准备姿势算起，还是从球被击出的瞬间算起？
- 结束：到球落地/出界，还是到球员恢复站位？

**对下游的影响**：Pass 1.5（技术分类）和 Pass 2（诊断）依赖这些时间段来聚焦分析。如果起始时间切入太晚（漏掉引拍），技术分类会丢失关键特征。如果结束时间切得太早（漏掉随挥），诊断会不完整。

### 问题 3："有效"与"无效"的灰色地带未覆盖

当前只列了两类极端情况。实际乒乓球视频中有大量灰色地带：
- 准备姿势/颠球热身 → 是否有效？
- 连续喂球中的短暂调整（教练换球筐）→ 是否应该断开？
- 失误后立即重新开始的极短停顿 → 是否应该合并？
- 慢动作回放 → 是否应该包含？

### 问题 4：`total_valid_seconds` 的计算规则不明确

提示词要求输出 `total_valid_seconds` 但没有说明计算方式。从 schema 看这是必填 NUMBER，但：
- 是所有 segments 的 `(end - start)` 之和？
- 还是去重后的总时长？
- 代码中 `validateSegments` 会过滤/截断片段，但模型计算的 `total_valid_seconds` 基于原始片段，**两者可能不一致**

> [!NOTE]
> 从代码看，`total_valid_seconds` 在 `validateSegments` 之后**并未被使用**（没有任何地方读取它），它只出现在日志中。但既然要求输出，至少应让模型知道准确的计算方式，以免其为了凑数而人为拉伸片段边界。

### 问题 5：时间格式说明不够严谨

提示词说 `"start": "mm:ss"`，但 `parseTimestamp` 同时支持 `mm:ss` 和 `hh:mm:ss`。对于超过 1 小时的视频（如完整比赛录像），需要使用 `hh:mm:ss` 格式，但提示词没有提及。

### 问题 6：缺少"单人/多人"场景的识别指引

从 Pass 2 的 `match_strategy` 分支可以看到，系统会区分"技术动作分析"和"比赛战术分析"，后者需要识别两位球员。但 Pass 1 的 `description` 中的"单球对练"vs"比赛回合"的区分标准是什么？当前提示词没有给出指引，可能导致模型在两种标签间随意切换。

### 问题 7：角色设定过于简单

当前的 system role 只是"专业乒乓球视频分析助手"，没有明确 Pass 1 的**唯一职责**——片段切割。模型可能会过度分析技术细节（虽然已限制了 description 不写技术名称，但模型的"思考"过程可能浪费 token）。

## 三、优化后的提示词

```
你是一名乒乓球视频片段切割专家。你的唯一任务是：观看视频，找出所有包含有效击球动作的时间段，过滤掉无效内容。
你只负责"在哪些时间段有人在打球"，不需要分析技术动作、评价好坏。

【有效片段的定义】
以下场景都视为有效：
- 正式比赛回合（从发球到得分）
- 单球对练（两人持续对打）
- 多球训练（教练/发球机连续喂球，球员连续击打）
- 发球练习（球员反复练习发球动作）
- 搓球/推挡等任何有球拍接触球的持续练习

【无效内容的定义】
以下场景必须排除：
- 捡球、等候、球员在球台间走动
- 休息、喝水、擦汗、聊天、看手机
- 调整器材（换球拍、调球网等）
- 纯慢动作回放（如果是比赛转播中穿插的回放）

【片段边界规则】
- 起始时间：从球员进入准备姿势（站定、举拍）的时刻开始，不要等到第一次击球才开始
- 结束时间：到最后一次击球动作完成（随挥结束、球员放松）时结束，不要在球刚出手就切断
- 如果两段有效击球之间的间隔 ≤ 5秒（例如短暂捡球后立即继续），应合并为一个片段
- 如果间隔 > 5秒，则分为两个独立片段

【description 规则】
description 只写以下场景类型之一，不要描述具体技术动作名称：
- "多球训练"
- "单球对练"
- "发球练习"
- "比赛回合"
- "综合练习"

【时间格式】
- 视频不足 1 小时：使用 mm:ss 格式（如 "02:15"）
- 视频超过 1 小时：使用 hh:mm:ss 格式（如 "01:02:15"）
- 时间精度以秒为单位，不需要更精确

【total_valid_seconds 计算方式】
total_valid_seconds = 所有 segments 的 (end - start) 秒数之和

如果视频内容完全不是乒乓球相关（例如：足球、篮球、日常生活等），请将 not_table_tennis 设为 true。
```

## 四、改动对照表

| 维度 | 原提示词 | 优化后 | 改进原因 |
|------|---------|--------|---------|
| 角色定位 | "专业乒乓球视频分析助手" | "片段切割专家"+ 明确唯一职责 | 减少模型过度分析技术细节的倾向 |
| 有效片段 | 简单列举 4 种 | 列举 5 种 + 补充"搓球/推挡等" | 覆盖灰色地带 |
| 无效片段 | 简单列举 6 种 | 7 种 + 明确慢动作回放策略 | 覆盖实际场景 |
| 边界规则 | ❌ 完全缺失 | ✅ 起始/结束精确定义 | 保证 Pass 1.5/2 能看到完整动作 |
| 合并策略 | ❌ 完全缺失 | ✅ ≤5 秒间隔合并 | 减少碎片化，降低片段数 |
| 时间格式 | 仅写 "mm:ss" | mm:ss + hh:mm:ss 规则 | 兼容长视频 |
| total_valid_seconds | 没有计算规则 | 明确 = 各段时长之和 | 消除歧义 |
| description | 举例 + "不要写技术名" | 封闭选项集 | 更可控，后续可枚举处理 |
| JSON 格式示例 | 完整 JSON 模板 | ❌ 移除（已有 responseSchema） | 减少 token 消耗，避免格式冲突 |
| not_table_tennis | 单独列出完整 JSON | 简洁一句话说明 | 减少 token，schema 已约束格式 |

## 五、关于代码侧的潜在配合优化（不在本次范围，备注参考）

> [!NOTE]
> 以下仅作为后续代码优化的参考思路，本次不做任何代码改动。

1. **`total_valid_seconds` 可考虑在代码侧计算**：与其依赖模型计算（可能不准），不如在 `validateSegments` 之后由代码自行计算。
2. **`validateSegments` 可增加合并逻辑**：即使提示词要求合并 ≤5 秒间隔，模型仍可能遗漏。代码中做二次合并更可靠。
3. **日志中 Pass 1.5 的解析 bug**：从日志第 107 行看到，第一个 Job 的 Pass 1.5 输出被包裹在数组中 `[{...}]`，解析后 `rawResult[0]` 取到了对象，但后续 `ClassificationResult` 构造时所有字段都变成了默认值（`unknown`, `0`, `[]`）。这可能是因为 `JSON.parse` 成功但取到的对象结构有问题——值得排查。
