# 视频分析评测集

用一批**你亲自标注过**的视频，客观比较不同模型（以及同一个模型不同时间）在这条链路上的表现，
作为「要不要换模型」「国内模型能不能上线」的依据。对应迁移计划 v2 的 W5 视频 Go/No-Go。

> 命令都在 `server/` 目录下运行：`cd server && npm run eval -- <命令>`
> 其中 `candidates` / `add` 要读数据库，需要 Node 22（和后端用同一个版本）。

> **给教练：用网页标注（推荐）**
> ```bash
> cd server && npm run labeler       # 浏览器打开 http://127.0.0.1:3100
> ```
> 左边选视频、右边看片点按钮取时间、下拉/勾选标注，改动自动保存回本文件。添加视频用页面右上角「＋ 添加视频」。
> 说明见 [labeler/README.md](./labeler/README.md)。下面是手工编辑 CSV 的方式，仍可用作复核和批量修正。

## 目录

```
eval/
  README.md                 本说明
  labels/annotations.csv    标注表（你填写，提交到 git）
  videos/                   视频文件（体积大，不提交到 git，换电脑要手动拷贝）
  runs/<日期-标签>/         每次评测的结果（results.json 原始结果 + report.md 报告，提交到 git）
  pricing.json              模型价格表（可选，参照 pricing.example.json 填写）
```

## 一、怎么建评测集（建议先做 30 条）

### 第 1 步：挑视频

```bash
npm run eval -- candidates
```

会列出本机已经上传分析过的视频（原文件名、时长、大小、**当时模型的判断**）。

> **标注时请自己看视频判断，不要照抄「当时的判断」。** 那是模型的输出，只用来帮你挑视频。照抄会让评测偏向这个模型。

**怎么挑，比数量更重要。** 30 条视频建议覆盖：

| 维度 | 建议 |
|---|---|
| 动作类型 | 知识库里常见的动作都要有；每个动作至少 2 条 |
| 容易混淆的对 | 反手拨球 vs 反手拉球、正手 vs 反手、拉球 vs 攻球。**这些是模型最容易判错的地方，要多放** |
| 有无教练语音 | 有清晰口令的、没有口令的、环境很吵的都要有 |
| 拍摄条件 | 不同机位（正面 / 侧面 / 斜后方）、光线（明亮 / 偏暗）、画质 |
| 无效视频 | 2–3 条没有有效击球的（纯讲解、捡球、非乒乓球），动作填 `none` |
| 左手持拍 | 至少 1–2 条（模型容易搞反方向） |

### 第 2 步：加入评测集

```bash
npm run eval -- add <任务ID> <video_id> --action <动作ID>
# 例：
npm run eval -- add b2d271d0 dapanpan2 --action bh_loop
```

- 任务 ID 取 `candidates` 列出的前几位即可（至少 8 位，写不唯一时会提示）
- `video_id` 是这个视频的短名，**只能用英文字母、数字、下划线、点、连字符**（建议用拼音），例如 `mashitong-b`
- 会自动把视频复制到 `eval/videos/`，并在标注表末尾追加一行
- `--action` 是你的判断；不确定可以先不写，之后在表格里填

> 视频不在本机（比如在公司电脑）：直接把视频拷到 `eval/videos/`，然后手工在标注表里加一行。

### 第 3 步：填标注表

用 Excel / Numbers / 任意文本编辑器打开 `eval/labels/annotations.csv`。**保存时选「CSV UTF-8」**，否则中文会乱码。

一行 = 一个视频。**留空 = 没标注**（这个指标会自动跳过这个视频）；**填 `none` = 明确没有**。

| 列 | 怎么填 | 示例 |
|---|---|---|
| `video_id` | 唯一短名（add 命令自动填） | `dapanpan2` |
| `video_file` | `eval/videos/` 下的文件名（add 命令自动填） | `dapanpan2.mov` |
| `action_id` | **最重要的一列。** 视频里的主要技术动作。必须是知识库里的 ID（见下面「查 ID」）；整段没有有效技术动作填 `none` | `bh_loop` |
| `segments` | 有效击球片段，`分:秒-分:秒`，多个用分号分隔。整段都没有有效击球填 `none` | `00:00-00:19; 00:25-00:40` |
| `has_voice` | 教练口令是否清晰可辨：`yes` / `no` | `yes` |
| `issues` | 这个视频**真实存在的主要问题点**，填诊断规则的 `issue_id`，多个用分号分隔；确认没有问题填 `none` | `bh_drive_net; bh_drive_elbow_unstable` |
| `tags` | 拍摄条件标签，自己定义，多个用分号分隔 | `side-view; dim-light; noisy` |
| `notes` | 备注 | `教练在旁边喊"拉"` |
| `source_job` | 来自哪个已上传任务（add 命令自动填） | |

**查 ID：**

```bash
npm run eval -- rules              # 所有动作及其问题点
npm run eval -- rules bh_drive     # 只看某一个动作
```

会列出每个动作的 `action_id`、每个问题点的 `issue_id`、对应的「看到的现象」和「问题」，标注时对照着选。

**填写原则：**

1. **`action_id` 先填，其他列可以慢慢补。** 只填 `action_id` 就能评测动作分类；补了 `segments` 才能评片段切割；补了 `issues` 才能评诊断。
2. **`segments` 以「有效击球」为准**，和 Pass 1 的 prompt 一致：包含击球前教练的口令和准备动作；不含捡球、休息、纯讲解、调整器材。不用精确到帧，到秒就行。
3. **`issues` 只填你确定看到的问题，填不全没关系，但别瞎填。** 注意这一列是按诊断规则来的：模型也只会从规则里挑问题，所以用同一把尺子才能比。规则之外的问题（比如「站位太靠后」）不用填。
4. **拿不准的视频，宁可把 `action_id` 留空，也不要乱填。** 不确定的标注会让评测结果失真。
5. 标注过程中**不要看模型的输出**，先标完再跑评测。

### 第 4 步：检查

```bash
npm run eval -- validate
```

会检查：格式是否正确、动作 ID 和问题点 ID 是否在知识库里、视频文件是否存在，并告诉你每一行哪里不对。

## 二、怎么跑评测

```bash
# 用当前 .env 里的模型配置跑一遍（每个视频 1 次）
npm run eval -- run --label gemini-baseline

# 指定模型（命令行优先于 .env）
npm run eval -- run --label argon --pass15 gemini-4-argon --pass2 gemini-4-argon

# 三个环节都用同一个模型
npm run eval -- run --label flash --all gemini-3.8-flash

# 每个视频重复 3 次，测稳定性（同一个视频同一个模型，多次结果是否一致）
npm run eval -- run --label argon --pass15 gemini-4-argon --pass2 gemini-4-argon --repeat 3 --yes
```

| 参数 | 说明 |
|---|---|
| `--label` | 这次评测的名字（必填），结果存到 `eval/runs/<日期>-<label>/` |
| `--all <模型>` | Pass 1 / 1.5 / 2 都用这个模型 |
| `--pass1` `--pass15` `--pass2` | 分别指定每个环节的模型，多个用逗号分隔（靠前优先，后面的是降级备选） |
| `--repeat N` | 每个视频重复 N 次，默认 1 |
| `--only a,b` | 只跑这几个 `video_id` |
| `--only-annotated` | 只跑已经填了 `action_id` 的视频 |
| `--yes` | 确认继续。**视频数 × 重复次数超过 6 时必须加**，防止误触发大额费用 |

> **费用提醒：** 每一次「视频 × 重复」都是一次完整分析（Pass 1 + 1.5 + 2 共 3 次模型调用，和你在界面上传一个视频一样）。30 个视频 × 3 次重复 = 90 次完整分析。第一次建议先 `--only` 挑几个小视频试跑。

每个视频只上传一次，重复运行共用这次上传，所以重复不会成倍增加上传时间。

### 对比两次评测

```bash
npm run eval -- compare eval/runs/2026-11-06-gemini-baseline eval/runs/2026-11-08-argon
```

只读取已保存的结果，**不调用模型、不花钱**。输出并排的指标表，以及逐视频的动作判断（✅ 全对 / ⚠️ 部分对 / ❌ 全错）。

### 加上价格后重新生成报告

填好 `eval/pricing.json`（参照 `pricing.example.json`，价格请以厂商官网为准）后：

```bash
npm run eval -- report eval/runs/2026-11-06-gemini-baseline
```

同样不调用模型。

## 三、报告里的指标怎么读

| 指标 | 含义 | 注意 |
|---|---|---|
| **动作分类准确率** | Pass 1.5 判断的动作和你标注的一致的比例 | 报告里给两个：「失败和降级计错」更严格，「仅已回答」只看模型给了答案的 |
| **自信地错** | 置信度 ≥ 0.75 仍然判错的次数 | **比普通判错更危险**：模型自己毫无察觉。迁移时重点盯这个 |
| **片段 IoU** | 模型切出的片段和你标注的片段在时间轴上的重合度（0–100%） | 同时给「模型原始输出」和「系统加缓冲合并后」两个值，前者衡量模型本身 |
| **起 / 终点误差** | 边界偏了多少秒，带正负 | 正数 = 模型比你标的晚 |
| **诊断问题点 F1** | 模型指出的问题点和你标注的 `issues` 的吻合度 | 只统计「动作判对」的运行；见下面的限制 |
| **JSON Schema 通过率** | 各环节输出格式合规的比例 | 迁移计划 Go/No-Go 门槛是 ≥ 95% |
| **分类稳定性** | 同一个视频重复跑，判断是否每次都一样 | 需要 `--repeat` ≥ 2。我们已经见过同一个视频、同一个模型一次判对一次判错 |
| **模型耗时 / 端到端估算** | P50 / P95 | 样本少时 P95 约等于最大值。端到端 = 模型耗时 + 上传 + 等待就绪 |
| **token / 费用** | 平均每次的用量和花费 | 费用需要自己填价格表，评测不内置价格 |

**诊断指标的局限：** Pass 2 的 prompt 要求「优先匹配诊断规则」，所以模型基本会照抄规则里的原话。评测把模型输出里包含「看到的现象」或「问题」原文的，算命中对应规则。如果换了一个喜欢改写措辞的模型，召回会被低估——到时需要引入 LLM 评分，目前没有。

**样本量：** 30 条视频只能发现明显的差距。两个模型准确率差 3 个百分点，不能说谁更好。看到「全错」「自信地错」这类具体的错误案例，比看百分比更有价值。

## 四、两件要趁早做的事

1. **采集 Gemini 基线，必须在服务器迁到国内之前。** 迁到国内后就访问不了 Gemini 了，没有基线就没法说国内模型「不低于 Gemini」。建议标注好 30 条后，立刻：
   ```bash
   npm run eval -- run --label gemini-baseline --repeat 3 --yes
   ```
   结果提交到 git 永久保存。
2. **评测集要稳定。** 一旦开始和模型对比，不要随便改已有视频的标注，要改就新开一个版本，否则新旧结果没法比。

## 五、线上任务也会留下记录

从 2026-11-06 起，每个视频分析任务（成功和失败的）都会把三个环节的原始输出、命中的模型、耗时和 token 用量存到数据库 `analysis_jobs.trace` 字段。以前 Pass 1.5 的结果只存在日志里，现在可以直接查，也可以拿来做线上数据的回顾分析。历史任务这个字段为空。
